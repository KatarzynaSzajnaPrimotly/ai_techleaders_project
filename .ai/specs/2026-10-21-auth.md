# Accounts and roles: GitHub and e-mail sign-in, role guards (E01, #29)

> Status: draft for review. Stories: #36 (S01 GitHub sign-in), #37 (S02 e-mail and password), #38 (S03 role guards, operator role).
> Depends on `2026-10-21-platform-foundations.md` (access policy, form layer, rate limiter, mailer, config, test kit). This is the shared auth spec the three stories name as owed before implementation; each story keeps its own acceptance criteria in its issue.

## 📝 TLDR

Nobody can be identified in DevMentor today: the session helpers exist, but no cookie is issued, there is no `users` table, and `POST /api/mentors` and `/admin/mentors` are public. This spec (future behavior) delivers sign-in with GitHub first and e-mail plus password as the fallback, one role per account (mentee, mentor, operator), a home screen per role, an operator role held only by the two founders, and the closing of every public write surface, built on the foundations spec.

## 📝 Problem Statement

- Who: mentees (developers with an urgent problem), invited mentors, and the operator (the two founders, D19). Interviews: a developer blocked before a release shipped a workaround (`research/2026-08-20-interview-working-dev.md`); a mentor says "my GitHub is my profile" (`research/2026-08-22-interview-mentor.md`); a fintech developer wants help "in twenty minutes, not create an account, verify the e-mail, then wait" (`research/2026-09-01-interview-backend-dev-fintech.md`). Sign-in friction is therefore itself a risk, and GitHub comes first.
- Code today: `core/src/http/auth.ts` signs and verifies a session JWT; nothing issues the `devmentor_session` cookie; the only migration creates `mentors`; no `auth` concept folder exists; `/api/mentors` GET and POST and `/admin/mentors` are public (the "known gap" in `AGENTS.md`).
- Rules (brief): D07/R06 GitHub first with e-mail fallback; D31/R23 exactly one role per account; D19/R18 the operator is the two founders and acts by hand where no story exists; R07/D08 mentors join by invitation only.

## 📝 Proposed Solution

Three phases, one per story, on the foundations primitives:

1. **S01** identity core: `users` table, session issuance, GitHub OAuth through a port, role homes.
2. **S02** password accounts, e-mail verification, rate limiting, the public forms.
3. **S03** operator derivation, `access` declared as role-restricted on the existing surfaces, scoping rule, public write surfaces closed.

Alternatives that lost: a server-side `sessions` table (instant revocation, but a read per request and a table the standards do not ask for; reopen if the founders need it, Q7); storing `operator` in `users.role` (it would be an assignable value, and R18 says there is no tool to assign it); combined roles per account (rejected by D31).

## 📝 Research

From general knowledge, not re-fetched in this run; direction, not evidence:

- Auth.js ships e-mail account linking off because linking on an unverified address is a takeover path. Adopted here: GitHub is linked to an existing account only through a verified e-mail on both sides (see Edge Cases).
- GitHub OAuth web flow: authorization code with a `state` value, `read:user user:email` scopes, e-mail from `GET /user/emails` (the `/user` e-mail can be null or unverified). We read the primary verified entry only. The state cookie is `HttpOnly`, `Secure` in production, `SameSite=Lax`, `Path=/api/auth`, expires after 10 minutes, and contains a purpose-tagged signed value bound to the browser flow. The callback validates the configured redirect URI and client before exchanging the code. PKCE is not required for the confidential server-side client in 1.0; this is an explicit trade-off, not an accidental omission.
- Mentor marketplaces (Codementor, MentorCruise) offer social sign-in; not re-checked here.
- Next.js 16 guide (bundled docs): guard in each page; `proxy.ts` only as an optimistic redirect.

## 📝 Architecture

New concept folders, created with their first file: `auth` (entities, repositories, services, validators, routes).

```mermaid
flowchart LR
    browser["Browser"] -->|"GET /api/auth/github"| ghroute["auth/github route (planned)"]
    ghroute -->|"redirect + signed state cookie"| github["GitHub (external)"]
    github -->|"code, state"| cb["auth/github/callback route (planned)"]
    cb --> usersvc["AccountService (planned)"]
    usersvc --> ghport["GithubIdentityPort (planned)"]
    ghport --> github
    usersvc --> repo["UserRepositoryPort (planned) to users table"]
    cb -->|"signSession, Set-Cookie"| browser
    browser -->|"cookie"| guard["requirePage / enforceAccess (foundations)"]
```

Takeaway: every sign-in path ends in the same `issueSession(user)`, so the cookie contract does not change per provider, and every guarded request goes through the foundations `enforceAccess`.

Components:

- `core/src/services/auth/account.service.ts` (`AccountService`): `findOrCreateFromGithub`, `verifyEmail`, `grantRole(userId, role: StoredRole)`.
- `core/src/services/auth/password-auth.service.ts` (`PasswordAuthService`, phase 2): `register`, `authenticate`; it uses `AccountService`, the password hasher and the mailer, and nothing else.
- `core/src/services/auth/user-repository.port.ts`, `user.types.ts`; implementation `db/src/repositories/auth/user.repository.ts` (maps 23505 to `ConflictError`; the entity is referenced by name, per the lesson on duplicate package copies).
- `core/src/services/auth/session-issuer.ts`: `effectiveRole(user, operatorEmails)` and `issueSession(user)` returning the token and the cookie string. One place decides the role in the cookie.
- `core/src/services/auth/github-identity.port.ts` and `adapters/github-identity.adapter.ts` (authorize URL, code exchange, `/user`, `/user/emails`; base URLs from config).
- `core/src/services/auth/password.service.ts` (bcryptjs), `email-verification.ts` and `oauth-state.ts` (signed purpose-tagged JWTs).
- Registered in `app/src/server/container.ts`: `userRepository`, `accountService`, `githubIdentity`, `passwordHasher`, `passwordAuthService` (one explicit line each; `rateLimiter` and `mailer` come from the foundations spec).
- Cross-system effects: E02-S01 (invitation accept) calls `grantRole` and `issueSession` to reissue the cookie; E03 onwards take `actor: Session` from `enforceAccess`. No event is emitted (no emitter exists; the catalogue assigns it to E03-S03).

### Role derivation

Stored role is `mentee` or `mentor` (a database check constraint). `operator` is never stored: `effectiveRole` returns `operator` only when the account's e-mail is in `OPERATOR_EMAILS`, the e-mail is verified (GitHub's verified primary, or `email_verified_at` set) and the stored role is not `mentor` (D31). An account on the list whose stored role is mentor signs in as mentor; the founder uses another address for the operator account. `grantRole` in turn refuses to grant `mentor` to an account whose e-mail is on the list. Two types: `Role = "mentee" | "mentor" | "operator"` for the session and guards, and `StoredRole = Exclude<Role, "operator">` for the column, the repository and `grantRole`, so the type system forbids storing `operator`.

### Guard layers

1. Route: `access` declared on every `apiHandler` and `makeCrudRoute` (foundations), roles equality only.
2. Page: `requirePage(access)` called in each page (foundations), redirect before any data fetch.
3. Record: services take `actor`, query by `actor.userId` and call `assertOwns` on every mutation. A client-supplied id never identifies the caller.

Role homes: mentee `/home`, mentor `/mentor`, operator `/admin/mentors`; `homeFor(role)` (in `app/src/server/guards.ts`, owned by the foundations spec) is the single mapping used by sign-in redirects and by the wrong-role redirect.

## 📝 Data Model

One new entity, `User` (table `users`, snake_case, UUID id, generated migrations, `up` and `down` tested). Two migrations: S01 creates the table, S02 adds the password columns (additive).

| Column | Type | Notes |
|---|---|---|
| `id` | uuid pk, `gen_random_uuid()` | |
| `email` | text, unique, stored lower-cased | login identifier |
| `email_verified_at` | timestamptz null | set from GitHub's verified primary e-mail or by the verification link |
| `display_name` | text | |
| `role` | text, default `mentee`, check in (`mentee`, `mentor`) | `operator` is derived, never stored |
| `github_id` | text unique null | GitHub ids are numeric; text avoids precision loss |
| `github_login`, `avatar_url` | text null | display only |
| `password_hash` | text null (S02) | bcrypt, cost 12 |
| `created_at`, `updated_at` | timestamptz | |

Sensitive data: `password_hash` and tokens never appear in API responses, logs, client-side application state, or plaintext database columns (the DTO that leaves the service is an allowlist without them). A verification token may be passed only to the mail adapter as part of the message body; access tokens remain inside the GitHub adapter boundary. The entity is independent of the existing `Mentor` entity; E02-S01 links an invited user to a mentor page later, so no relation is drawn here and no graph is generated (one entity, no relation to existing ones).

## 📝 API Contracts

All routes use `apiHandler` and `force-dynamic`. Normal API errors and data use the envelope `{ ok, data | error }`. OAuth start/callback, e-mail verification, and logout are explicit exceptions where the handler may return a redirect and/or `Set-Cookie`; those responses still go through the shared error logging and typed error mapping.

| Route | Method | Access | Behavior |
|---|---|---|---|
| `/api/auth/github` | GET | public | Sets the signed `state` cookie (purpose `oauth-state`, 10 min, includes a sanitised `returnTo`), redirects to GitHub. 503 when the GitHub variables are missing. |
| `/api/auth/github/callback` | GET | public | `error=access_denied` redirects to `/sign-in?cancelled=1`, creates nothing. Missing or mismatched `state` redirects to `/sign-in?error=state`. No verified e-mail redirects to `/sign-in?error=no-verified-email`. Success: find or create, `issueSession`, `Set-Cookie`, redirect to `returnTo` or `homeFor(role)`. |
| `/api/auth/register` | POST | public, rate limited | `{ email, password, displayName, returnTo? }`; always answers "check your e-mail", whatever the address. A new address gets an unverified account and the verification mail; an address that already exists (password or GitHub) changes nothing and gets a mail saying the account exists and how to sign in (with GitHub when the account has a `github_id`). |
| `/api/auth/login` | POST | public, rate limited | `{ email, password }`; every failed attempt (unknown e-mail, wrong password, or unverified e-mail) has the same generic `UnauthorizedError("Invalid credentials")`; no session before `email_verified_at`; sets the cookie only on success. |
| `/api/auth/verify-email` | GET | public | `?token=`; verifies the purpose-tagged token. An atomic conditional update changes `email_verified_at` only when it is null; only the request that updates one row issues the session and redirects to `returnTo` or the home. Any later or concurrent use of the same link issues nothing and redirects to `/sign-in`, so a forwarded or archived link is not a login. |
| `/api/auth/logout` | POST | authenticated | Clears the cookie (CSRF header required). |

Validation (Zod, in `core/src/validators/auth/`, exported also through `@devmentor/core/validators`): `register.schema.ts` (`email`; `password` at least 12 characters and at most 72 UTF-8 bytes because bcrypt ignores the rest; `displayName`; `returnTo` optional), `login.schema.ts`. `returnTo` accepts only a single-slash relative path (not `//`, not absolute, no backslash); an invalid value is rejected, never silently rewritten. The GitHub `state` and the verification token are separate purposes of the same secret, so a session token is never accepted as either and the reverse.

Cookie: existing name, HS256 and 24 h. `Secure` is set when `APP_URL` starts with `https://` (the integration run is served over plain http, where a `Secure` cookie would not be stored).

Existing surface changes in phase 3 (breaking for anonymous callers, listed in the PR body): `GET` and `POST /api/mentors` become `access: { roles: ["operator"] }`.

## 📝 UI/UX

Only the unique parts.

- Skin rule (foundations): public pages use Tailwind, every page behind a session uses shadcn, so `/home` and `/mentor` are shadcn and `/sign-in`, `/register` are Tailwind.
- `/sign-in` (Tailwind, `PublicForm`): GitHub button first, e-mail form second (D07). Distinct, plain messages for `cancelled=1`, `error=state`, `error=no-verified-email`; one generic message for a failed password sign-in; a "check your e-mail" state after register. A signed-in visitor opening `/sign-in` or `/register` is redirected to their home. The e-mail fallback is disabled with a note until phase 2 lands, so phase 1 ships a working page.
- `/register` (phase 2), `/home` (mentee), `/mentor` (mentor). Each page calls `requirePage`. No link, route or copy anywhere offers "become a mentor" (R07).
- Sign-out: a button on each role home calls `POST /api/auth/logout` through `apiCall`, then navigates to `/sign-in`.
- Accessibility: labelled inputs, errors in `role="alert"`, GitHub button is a real link (navigation, not `fetch`), focus order GitHub then form.
- States: loading (submit locked), error (generic or specific as above), success redirect. No empty state exists yet.
- Route groups `(auth)`, `(mentee)`, `(mentor)`; the engineering standards' sample `(student)` becomes `(mentee)`.

## 📝 Edge Cases & Failure Scenarios

| Case | Result |
|---|---|
| User cancels at GitHub | `/sign-in?cancelled=1`, no account, plain message |
| Missing, mismatched or expired `state` | no session, no account, `/sign-in?error=state` |
| GitHub returns no verified primary e-mail | no account, told why |
| GitHub variables missing | 503 on the GitHub routes; e-mail sign-in unaffected |
| GitHub API down or non-2xx | `ServiceUnavailableError`, logged without the code or token, message tells the user to retry or use e-mail |
| Account exists by e-mail, unverified password registration, GitHub sign-in with the same verified e-mail | the operation runs in one transaction: the unverified account row is removed, a GitHub identity is created for the verified e-mail, and the old token becomes invalid because its account no longer exists; no unverified account is linked |
| Account exists by e-mail and is verified, GitHub sign-in with the same verified e-mail | linked to that account (`github_id` set), same user |
| Register with an e-mail that already exists (GitHub or password account) | identical "check your e-mail" response; no account changed; the owner gets a mail saying how to sign in (GitHub hint when applicable). Story #37's criterion "refuse and point to GitHub" is replaced by this, because a refusal discloses which addresses are registered |
| Mail delivery fails during registration or verification-mail resend | the account remains unverified and retryable; the operation returns `SERVICE_UNAVAILABLE` without revealing whether the address exists; retries are idempotent and never create a second account |
| Old verification link used again | no session, redirect to `/sign-in` |
| Wrong password or unknown e-mail | identical `UnauthorizedError`, a dummy bcrypt comparison keeps timing equal, no `Set-Cookie` |
| Unverified e-mail tries to sign in | no session; the same generic invalid-credentials response as an unknown e-mail or wrong password; any resend-verification flow must not reveal account existence |
| Rate limit reached | 429 `RATE_LIMITED` with `Retry-After`; no counter reveals whether the account exists |
| Expired or tampered cookie on a guarded page | redirect to `/sign-in`, nothing of the page rendered |
| Wrong role on a guarded page | redirect to that role's home; on a route 403 |
| Operator e-mail on the list but unverified | not operator |
| Operator e-mail whose account is mentor | mentor only (D31) |
| Concurrent first sign-ins for one GitHub id | unique `github_id` and `email` constraints; the loser retries the lookup once and returns the winning account when visible, otherwise fails with `ConflictError`; covered by an integration test (check-then-write rule) |
| Concurrent e-mail verification requests | a conditional `UPDATE ... WHERE email_verified_at IS NULL` allows exactly one request to transition the account and issue a session; all other requests issue no session and redirect to `/sign-in` |
| Removed from `OPERATOR_EMAILS` | effective at next sign-in, an existing cookie lasts up to 24 h (Q7). Before payouts or disputes go live, introduce revocation or a shorter operator-specific lifetime; emergency removal uses `JWT_SECRET` rotation and therefore revokes every session |
| OAuth `state` cookie | cleared in the callback on every outcome; a replayed callback finds no cookie and fails as a state mismatch |
| `returnTo` absolute or protocol-relative | request rejected |

## 📝 Risks & Impact Review

- **Hard to reverse: the `users` table and the cookie claims.** The cookie name, algorithm and claim names stay; only `role` validation tightens. No token is issued today, so no live session breaks. Rollback of S01 and S02: migration `down` drops the table and columns; S03 rollback restores the public routes (a security regression, so it is never reverted without a replacement guard).
- **Breaking, intended:** `GET` and `POST /api/mentors` need an operator session. The in-repo caller `AdminMentors` and `mentors.int.test.ts` change in the same PR. `/mentors` reads through the service, not the API, so it keeps working. It also prints mentor e-mails publicly, which is a separate privacy question for E02 and not changed here.
- **Account takeover by e-mail linking:** mitigated by the verified-on-both-sides rule and the transactional replacement rule; covered by tests in S02, including concurrent registration/linking.
- **Stateless sessions (Q7):** no instant revocation; accepted by the user, documented in the operator note (R18).
- **New dependency:** `bcryptjs` (pure JavaScript, no native build in CI), added to `packages/core/package.json` with a lockfile change and `npm audit`; compatibility with the Next 16 server bundle is unverified and is checked in S02 step 1.
- **Operator revocation:** removing an address from `OPERATOR_EMAILS` does not invalidate an existing stateless JWT for up to 24 hours. This is an explicit MVP security limitation; before payouts or disputes go live, add server-side revocation or shorten the operator session lifetime. Emergency removal requires rotating `JWT_SECRET`, which signs out every account.
- **Operator by allowlist:** the founders edit `OPERATOR_EMAILS` by hand and log it (R18); a typo grants nothing (verified e-mail is also required). Removing an address does not revoke an existing stateless token until expiry.
- **Story text superseded:** issues #36 to #38 name `authorize`, `requirePageRole(role)`, a `UserService` and a widening `Role`; this spec replaces them with `access`, `requirePage`, `AccountService`/`PasswordAuthService` and a three-value `Role`, and #37's "refuse and point to GitHub" criterion with the uniform register response. Update the issue bodies when the spec merges.
- **Protected surfaces touched** (`BACKWARD_COMPATIBILITY.md`): Session cookie and JWT, Environment variables and config, HTTP API routes, Database schema and migrations, Package public exports, Shared Zod schemas. Labels `risk-high`, `needs-qa`; second reviewer; no self-QA. Security-relevant fixes say so in the PR.
- **Direction calls vs rule violations:** the defaults below are product calls (owner founder A); nothing here violates a repository rule.

### Assumptions taken as defaults (non-blocking, confirm in review, owner founder A)

- E-mail must be confirmed before sign-in, not only before booking (the story criteria assume this; friction cost noted by the fintech interview). The external login failure remains generic for unknown, wrong-password, and unverified accounts to prevent enumeration.
- Mail transport for 1.0 is the log adapter selected by `MAILER_TRANSPORT=log` (development and the integration harness only); a real transport is needed before invitations go out (brief Q26, launch blocker, not a spec blocker).
- Rate-limit keys: client IP from the first `x-forwarded-for` entry only when `TRUST_PROXY` is true, otherwise one shared `unknown` IP bucket. Two limits apply per endpoint (foundations): per (IP, e-mail) and per IP alone. Named constants with the reason: login 5 failures per 15 minutes per (IP, e-mail) and 30 per 15 minutes per IP; register 5 per hour per IP. The per-IP numbers are a starting point to tune.
- GitHub flow uses `state` only (confidential client with a secret); PKCE is not added in 1.0 as an explicit trade-off. The state cookie security attributes, purpose, expiry, browser-flow binding, configured client, and redirect URI validation are mandatory.
